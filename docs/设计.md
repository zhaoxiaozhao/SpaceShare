# 公益共享座位平台——技术设计说明

## 1. 总体架构

目标：

> 低成本起步、无状态水平扩展、数据模型可扩展到全国城市和多种公共空间。

推荐：

- 小程序：微信原生小程序 / Taro（二选一）
- 后端：ASP.NET Core 10 Web API
- ORM：EF Core
- 数据库：PostgreSQL
- Redis：缓存、分布式锁、限流
- 对象存储：OSS/COS/S3兼容存储
- CDN：图片和静态资源
- 管理后台：Vue 3 + TypeScript
- 部署：Docker Compose 起步
- Nginx：反向代理
- 日志：Serilog
- 定时任务：Hangfire
- API文档：OpenAPI/Swagger

优先选择自己熟悉的 .NET 技术栈。

# 16. 核心预约并发控制

这是系统最重要的技术部分之一。

错误实现：

```text
查询座位
↓
发现空闲
↓
插入预约
```

高并发下会出现：

> 两个人同时预约成功。

必须使用：

```text
请求
 ↓
Redis分布式锁
 ↓
数据库事务
 ↓
检查时间段
 ↓
创建Reservation
 ↓
提交
 ↓
释放锁
```

锁Key示例：

```text
seat:reservation:{seatId}:{date}
```

锁时间必须短。

最终数据库仍然是事实来源。

---

# 17. 时间段冲突

预约必须满足：

```text
new.start < old.end
AND
new.end > old.start
```

如果成立：

> 时间冲突。

对于PostgreSQL优先使用：

```text
tstzrange
```

配合EXCLUDE约束。

这样可以从数据库层阻止并发时间重叠。

---

# 18. 自动释放

后台定时任务每分钟执行：

```text
查找
status = reserved
且
now > start_at + grace_period
```

执行：

```text
reserved
 ↓
no_show
 ↓
释放share
 ↓
通知候补
 ↓
扣信用
```

不要依赖用户主动操作。

---

# 19. Redis使用范围

Redis只负责：

- 分布式锁
- 热门座位缓存
- 图书馆可用座位缓存
- 限流
- 验证码/临时数据
- 风控计数

不要把核心预约数据只放Redis。

# 31. 测试重点

必须重点测试：

### 并发预约
100～1000个请求同时预约同一个座位。

结果：

> 只能一个成功。

### 自动释放
用户不确认到达：

> 自动释放。

### 时间冲突
不同用户预约重叠时间：

> 不能成功。

### 重复预约
同一用户同时预约多个座位：

> 拒绝。

### 取消
取消后：

> 座位立即进入可预约状态。

### 候补
第一用户取消：

> 候补正确通知。

### 风控
大量预约：

> 自动限流。

# 34. 技术设计原则

1. 第一版采用单体模块化架构，不做微服务。
2. API必须无状态。
3. PostgreSQL/MySQL是核心事实数据库。
4. Redis只负责缓存、锁和限流。
5. 预约并发控制必须数据库事务 + 分布式锁双保险。
6. 所有核心业务必须可审计。
7. 所有规则尽量配置化。
8. 座位模型必须支持未来扩展到公共空间。
9. 用户隐私最小化收集。
10. 不设计站内聊天。
11. 不允许座位交易。
12. 赞助与预约权限完全解耦。
13. 先模块化单体，业务规模达到瓶颈后再拆服务。
14. 所有时间统一使用UTC存储，展示时转换到场馆本地时区；如果早期仅服务中国，可统一Asia/Shanghai，但数据库设计仍建议保留时区意识。
15. 核心业务优先保证一致性，再考虑极致性能。
